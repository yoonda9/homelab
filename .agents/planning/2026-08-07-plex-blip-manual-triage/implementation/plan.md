## Step 1: Repair the watchdog's diagnostic probes

**Objective.** Make the two lock-holder probes work. `fuser` has failed on 34 of 34
invocations because `psmisc` is not installed; `lsof` times out in 12 of 12 in-blip
snapshots against a hard 0.5 s limit. The tool currently captures lock-holder data
exclusively when nothing is wrong.

**Guidance.** Add `psmisc` to the package list in `ansible/roles/plex/tasks/main.yml`.
Change `_run_cmd` to return the structured result defined in design §5.1 —
`{status, elapsed_ms, output, error}` — with `status` distinguishing `ok` / `timeout` /
`missing` / `error`. Raise the default timeout to 2.0 s, per-probe overridable. Record
`elapsed_ms` **even on timeout**: `lsof` crossing a threshold on the database files is
itself a contention signal, and it is currently discarded. Update `capture_snapshot`
to store the structured shape; keep every existing top-level JSONL key so the 448 KB
of captures already on disk stay parseable.

**Tests** (`scripts/test_plex_blip_watchdog.py`):
- A command that sleeps past the timeout → `status == "timeout"` **and**
  `elapsed_ms ≈ timeout × 1000`. This is the regression that matters most: the old
  code lost the number.
- A nonexistent binary → `status == "missing"`, distinct from `"error"`.
- A successful command → `status == "ok"`, output preserved, `elapsed_ms > 0`.
- A snapshot dict round-trips through `json.dumps` with the new `lock_holders` shape.
- Existing tests still pass unmodified.

**Integration.** First change to the codebase; nothing depends on it yet. Everything
in Steps 2–4 writes into the snapshot structure defined here.

**Demo.** Deploy with `just play`, trigger the watchdog (a `Completed: ≥500 ms` line
suffices), and show a JSONL snapshot containing **real `fuser` output for the first
time since deployment**, alongside `lsof` with a recorded `elapsed_ms`.

## Step 2: Capture the causal log line

**Objective.** Record `Held transaction for too long (<site>): N seconds` — the
holder-side signal that names the offending code site in its own text, and is matched
by neither existing tool. With `fuser` and `lsof` both failing during stalls (Step 1
fixes that, but the log line is free and always available), this is the only source of
holder attribution that has ever worked.

**Guidance.** Add a `TX_HELD` branch to `check_trigger` in the watchdog and the
mirroring condition in `parse_log_line` in `scripts/analyze_plex_blips.py`, extracting
`hold_site` (e.g. `StatisticsManager.cpp:288`) and the hold duration. In both tools,
also extract the `(N live)` connection count that every `Request:`/`Completed:` line
already carries. In the analyzer, report **holders and waiters separately** — the
current summary shows 9,450 ms of total lock delay against requests that stalled
108,832 ms, which reads as a contradiction until you realise it measures the ripple
rather than the stone.

Do **not** justify this as making the watchdog fire earlier. It does not: the
`Completed: ≥500 ms` rule already fired 52 ms after the first slow completion on
2026-08-07. The value is classification and attribution.

**Tests** (`scripts/test_plex_blip_watchdog.py`, `scripts/test_analyze_plex_blips.py`),
using **real lines from `/tmp/plex-logs/2026-08-07/`** as fixtures:
- The genuine 06:37:33.273 line → `event_type == "TX_HELD"`, `delay_ms == 540.0`,
  `hold_site == "StatisticsManager.cpp:288"`.
- A `MetadataItemSetting.cpp:459` line → correct site extraction with a `[Req#…]` prefix.
- Regression: a real `Took too long` line still yields `TX_STALL`, unchanged.
- A real `(13 live)` line → `live_connections == 13`.
- Analyzer over a slice of the 08-07 log → holders and waiters counted separately, and
  `TX_HELD` appears in the taxonomy table.

**Integration.** Writes `hold_site` and `live_connections` into the Step 1 snapshot
structure. The analyzer change makes the existing 92 MB of logs re-analysable with the
new attribution.

**Demo.** Re-run `analyze_plex_blips.py` over the 2026-08-07 log and show the report
naming `StatisticsManager.cpp:288` as the first holder at 06:37:33 — an attribution
the tool could not previously produce — plus the 5 → 13 → 3 saturation curve.

## Step 3: Make WAL state visible and guarded

**Objective.** Surface the leading indicator of the open root cause. The WAL is
41.71 MiB against a 40.9 MiB database — 43× SQLite's default checkpoint threshold —
and has been byte-identical for 42.5 hours. Today's audit asserts `journal_mode == 'wal'`,
which is **true**, and passes green while this is live.

**Guidance.** Add WAL state capture to the watchdog snapshot (`os.stat` on the three
database files — no connection, no lock, no writer). Replace the Ansible audit so it
asserts **both** journal mode and `wal_bytes < plex_wal_max_bytes` (default
`8388608`), failing the play with both the observed and threshold values in the
message. Correct `docs/runbooks/plex-sqlite-maintenance.md`, which currently claims
WAL mode exists "to prevent transaction lock stalls" — we have now measured WAL mode
enabled *and* stalls occurring, so the claim must be strengthened to "necessary but
not sufficient; an unchecked WAL is itself a stall mechanism."

**Tests:**
- `_wal_state` against temp files of known size → correct byte counts and `wal_ratio`.
- Missing WAL file → the `sqlite` block is omitted and the snapshot is still written
  (a nice-to-have must never abort a capture).
- Ansible guard, molecule-style or via a shape test: a **41.71 MiB** WAL **fails** the
  task, and a 2 MiB WAL passes. The failing case is the important one — a guard is
  only proven by watching it go red.
- A runbook shape test asserting the corrected claim is present, following the
  existing `test_plex_*_runbook_shape.py` convention.

**Integration.** Extends the Step 1 snapshot; the guard runs in the existing plex role
play.

**Demo.** Run `just play` and show the WAL audit **failing** against the live
41.71 MiB WAL, naming both numbers. The guard that has been green over a live fault
now goes red.

## Step 4: node-exporter in CT 110 and watchdog metrics into Prometheus

**Objective.** Move watchdog findings off CT 110's local disk and onto the Prometheus
timeline, so "was there a lock hold at T?" becomes a Grafana question rather than an
SSH question. Simultaneously close the class-C blind spot (load average, D-state
count, PSI) with a time series and a baseline.

**Guidance.** Deploy `node-exporter` inside CT 110 by Ansible as a systemd unit with
`Nice=10` / `CPUSchedulingPolicy=idle`, mirroring the watchdog unit; disable collectors
that are meaningless in an unprivileged LXC rather than fighting them. Have the
watchdog emit the textfile metrics of design §5.2 via atomic write-and-rename into the
collector directory. Add the Prometheus scrape job at 15 s.

Include `plex_watchdog_probe_status` — the metric that would have surfaced the missing
`psmisc` on day one instead of at 34 failures.

**Tests:**
- Textfile output parses with `prometheus_client.parser.text_string_to_metric_families`.
- Golden-file comparison for exposition format, including `# HELP` / `# TYPE`.
- Write is atomic: a partial write never leaves a truncated `.prom` in place.
- Counters are monotonic across successive snapshots; `plex_sqlite_wal_bytes` reflects
  the Step 3 capture.
- Ansible idempotence: a second `just play` reports no changes.

**Integration.** Consumes Steps 1–3 (probe status, `TX_HELD` counts, WAL bytes) and
publishes them. First step where the repaired tooling becomes visible outside CT 110.

**Demo.** `plex_sqlite_wal_bytes` graphed in Grafana at its true 43,735,168 — the
pathology, on a dashboard, for the first time. Alongside it,
`plex_watchdog_events_total{event_type="TX_HELD"}` and
`plex_watchdog_probe_status{probe="fuser"} == 1`.
